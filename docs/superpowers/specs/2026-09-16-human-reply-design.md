# human-reply design

A skill that drafts messages in the user's own voice for the channels where
they talk to colleagues: Slack, GitHub, and Notion in version one. A guided
setup collects a sample of the user's real messages from each connected
channel, filters out the ones that read as AI-written, measures them, and
writes a per-channel voice profile. At runtime the skill works out which
channel a message is for, loads that channel's profile, and drafts inside
its budget and shapes. It produces text only and never posts.

It replaces `slack-reply`, whose Slack facts (surface tiers, shapes,
markup pitfalls, audit list) move into this skill's Slack channel module
and whose per-person numbers, phrasebook, and examples are regenerated by
setup instead of living in the repo.

## 1. Goals and non-goals

Goals:

- A colleague with a bare Claude Code install and one connected channel
  can run setup in about thirty minutes and get drafts that read as their
  own writing, not as a template with their name on it.
- Every number in a profile is measured from the person's messages when
  Python is available and the surface clears the 30-record floor, and
  labelled as an estimate otherwise, whether Python is absent or the
  surface is too thin.
- Messages the person drafted with AI tools do not feed the profile. The
  filter is a date the person supplies plus a scaffolding scan on long
  messages after that date.
- A person can adopt named traits from a colleague's writing at setup.
  Once adopted, those traits are the person's voice; the runtime does not
  distinguish them.
- Runtime states the channel, surface, budget, and profile provenance in
  its first line, so a wrong channel guess is visible before anything is
  pasted.
- The skill never calls a send tool. The person posts the draft.

Non-goals:

- Posting on the person's behalf. Version one is text only on every
  channel. Posting adds a tool surface and a read-back step per channel
  and a mistake class that cannot be undone, none of which is about voice.
- Email, Azure DevOps, or any channel beyond the three named.
- Multi-turn conversation. The skill composes one message from the thread
  context it is given. It does not keep replying.
- A full corpus. Collection is capped per channel; the profile states its
  sample size and window so nobody mistakes it for a census.
- Replacing `pr-watch`'s posting contract. `pr-watch` keeps the rules that
  say what a posted reply must carry and must never say; this skill
  supplies the wording when installed (section 6), and the contract's
  items reach it only as content in the ask, never as rules it reads.

## 3. Setup

`/human-reply setup [channel]` runs once per person, or again to add a
channel or rebuild one. Each step is one file under `setup/`. Interview
questions go one per turn.

### 3.1 Detect

Probe what is connected and report a table before asking anything:

| Channel | Probe | Collector |
|---|---|---|
| Slack | the Slack search tool is listed | month-windowed search, `from:<@me>` |
| GitHub | `gh auth status` exits 0 | `gh api` and `gh search` |
| Notion | the Notion tools are listed | recent pages walk, comments per page |

Also probe `python3` then `python`. If neither runs, say that the measuring
step will run inside the model instead, that this costs more tokens and
produces estimates rather than counts, and offer the install link. The
person chooses to install and rerun, or to continue on the fallback. The
choice is recorded in the profile header as `method: measured` or
`method: estimated`.

The person picks which of the connectable channels to set up. A channel
whose tool is not connected is listed as skipped in the final summary,
never silently absent.

### 3.2 Interview

One question per turn, in this order:

1. When did you start drafting messages with AI tools? A month is enough.
   Everything before it is trusted; everything after it and over sixty
   words gets the filter. "Never" means no cutoff and no filter on the
   person's own messages. When the cutoff falls before the sample window
   starts, setup says the budgets would have nothing pre-cutoff to
   measure from and offers to widen the window before continuing.
2. Who is your inner circle on Slack? Names of the people you DM most.
   Skipped when Slack is not being set up. Used for the inner-circle DM
   surface; without it every DM is an outer DM.
3. Sample window. Default the last twelve months. With a cutoff month,
   the question says months before the cutoff are collected first.
4. Is there a colleague whose writing you want to borrow from? Name, and
   which channel to read them on. Optional. When a colleague is named,
   one follow-up: have you told them their messages will be read for
   this? The borrow collector runs only on a yes, and the yes is recorded
   with the colleague's name and the date under Borrowed traits.

### 3.3 Collect

Each channel writes `~/.claude/human-reply/corpus/<channel>.jsonl`, one
record per message, in the shape from `human-reply/references/corpus-record.md`:

```
{"channel": "slack", "surface": "channel thread reply", "ts": "2026-03-04T10:12:00Z",
 "audience": "C0123", "thread": "C0123/1709546000.1", "text": "...", "held_out": false}
```

`surface` is assigned by the collector from the channel module's surface
list (section 4.2). `audience` is the channel, repo, or page id, not a
person's name. `thread` identifies the conversation the message belongs to
so calibration can reconstruct context.

Slack: one calendar month per search window, channels and DMs as separate
windows, re-windowed from the last captured date minus one day when a
window hits the 20-page cap. Capped at 1,500 records. An early empty page
ends a window only when the previous page was also short. The `from:`
query uses literal angle brackets; the HTML-entity form returns "No
results found" with no error, so a month where both windows come back
empty is re-run once after checking the query, and a month still empty is
recorded and named in the collect report. Messages in the person's own
self-DM and messages with no text after trimming are skipped.

With a cutoff month, Slack and Notion collect in two passes so the cap
fills with the pre-cutoff messages budgets are measured from. The first
pass runs from the last day of the month before the cutoff back to the
window start and stops at the cap. The second runs only when the first
ended below the cap, from the window end back to the first day of the
cutoff month, and stops at the cap. Within a Slack pass each month gets a
quota, the room left under the cap divided by the months in the pass,
so 1,500 records cover the whole pass rather than its newest three
months; the channels window takes at most half of a month's quota and
the DM window the rest. `scripts/corpus.py normalize` takes the cutoff on
every call, including GitHub's: when it trims to the cap it keeps
pre-cutoff records first, then fills the remaining room with post-cutoff
records, and on each side it takes the newest record of every month in
turn, so a busy month cannot crowd out the others. It drops records
whose text is blank and decodes the `&lt;`, `&gt;`, and `&amp;` Slack
returns for typed characters. The pass in progress and its quota are stored in
setup state so a resumed run continues it.

GitHub: `gh search prs` with `--author @me`, `--reviewed-by @me`, and
`--commenter @me`, plus `gh search issues --commenter @me`, together list
the repos, so a person who mostly reviews is found in repos where they
never opened a PR; for each repo, `gh api` pulls the person's review
comments, review summaries, PR bodies, and issue comments in the window.
Capped at 1,500 records.

Notion: walk the person's recent pages, pull their comments on each. This
is the weakest collector, capped at 500 records, and the profile header
says so.

Automated posts: automations that post under the person's name would
teach the profile their status lines. After collection,
`scripts/corpus.py templated` flags every audience with at least ten
records where half or more open with the same three words. The person
sees each flagged audience with its channel name, record count, and
prefix, and answers one question: which are automated posts to leave out,
naming any other channels too. `scripts/corpus.py drop` removes the chosen
audiences, and the collectors skip them on any later rerun.

Colleague sample: the same collector on the named channel with the
colleague as author, capped at 300 records, written to
`corpus/borrow-<channel>.jsonl`. It runs at the start of the colleague
pass in the read step (section 3.6), not here, so the file is collected,
filtered, read, and deleted in one step.

Every record passes through `scripts/redact.py` before it is written.
Private-key, token, key, password, and connection-string patterns become
`<redacted:kind>` placeholders, and so do URL `pwd=` values, cookie
values, and Bearer tokens (section 8). The summary states how many records were
touched. On the no-Python path the model applies the same pattern list,
and before the first record is written it must redact the known-bad
fixture from section 9 with no miss; a miss stops setup and says Python
is required to collect. A corpus redacted by the model is never offered
the `keep` choice at finish, and the channel header records
`redaction: model`.

Hold-out: before anything else reads the corpus, three threads per set-up
channel that the person replied to are marked `held_out: true`, chosen at
random from pre-cutoff threads (the whole window when there is no cutoff)
with at least one other participant within the record's thread id, so
thread replies and two-person review threads qualify. A Slack DM message
outside a thread is its own thread id with nobody else in it, so it does
not. A thread holding a PR body does not qualify, because calibration
drafts a reply to someone else's message and a PR body answers nobody,
and neither does a thread whose only record of the person is its opening
post. Calibration fetches each thread through a subagent that returns
only the context before the person's reply, so the draft is written
before the real reply is seen.
When a channel has a cutoff and fewer than three such threads,
the remainder come from post-cutoff threads whose reply passes the
filter, and the calibration prompt says which pool each thread came from.
A channel still short of three is backfilled at calibration (section
3.7). Held-out records
are excluded from measure and read, and used only in calibration.
Calibration compares the draft against what the person actually wrote, so
a held-out reply that was itself AI-drafted would teach the profile the
wrong voice.

### 3.4 Filter

`human-reply/references/ai-filter.md` defines the scoring mechanism and the
threshold. The pattern list is per channel and lives in that channel's
module, because the tells differ by platform: headers, labelled bullets,
and a closing summary are the native form of a PR body or a Notion page
comment, and a Slack-shaped list would gut those surfaces before they are
measured. The scan runs on the person's messages that are after the
cutoff and over sixty words, and on every colleague message over sixty
words. Each pattern the channel lists scores one point.

The Slack list, seeded from the author's corpus notes:

- emoji used as a section marker at the start of a line
- a TL;DR or summary block before the body
- "Key highlights", "Key takeaways", or a labelled bullet list
- bold labels or markdown headers
- an em dash
- three parallel items in a row where the person's short messages never
  use bullets
- a closing sentence that restates the message
- two or more words from the humanizer skill's vocabulary list
- a "not X, but Y" construction

The GitHub and Notion lists start from the same set minus headers,
labelled bullet lists, and the closing summary on the PR body, review
summary, and page comment surfaces, where those are the native form. They
add nothing until a corpus shows a platform-specific tell.

A message scoring three or more is dropped. The person sees the drop count
per channel and five dropped samples, and may adjust the threshold once
before continuing: lower it freely, or raise it by at most one point. A
threshold other than the default is written into the channel profile
header as `threshold: <n>` so a loosened filter is visible downstream.

The drop rate is dropped messages over scanned messages; the rate over
all of a channel's messages is shown but gates nothing. The drop rate is
read twice. The first read, before any adjustment, decides whether the
two-cause prompt shows: over 40 percent of scanned messages, the prompt
names a wrong cutoff date and a person who writes in this shape by
default, and the person picks re-asking the date or raising the
threshold (that is the one adjustment). The second read, after the
adjustment, decides the outcome: a rate still over 40 percent of scanned
messages does not
loop; setup proceeds with the filtered set, marks the channel `partial`
in the profile header, and says why.

### 3.5 Measure

`scripts/measure.py` reads a channel's JSONL and writes
`corpus/<channel>.stats.json`:

- word counts per surface at median, 75th, and 90th percentile, with links
  and code blocks collapsed to one token each
- share of messages over the surface budget
- pattern rates over messages longer than sixty words: opener, sign-off,
  cc line, bullets, hedge, question, link, code span, fenced block, bold,
  quote-reply, emoji
- per-quarter 90th percentile and share over 150 words
- the list of message ids over sixty words, for the read step

The fallback path has one sonnet subagent per channel estimate the same
fields from a 300-message stratified sample, reporting each number as a
bucket (for example "median 15 to 25 words") and every rate to the nearest
ten percent. `stats.json` gets `"method": "estimated"`.

### 3.6 Read

Sonnet subagents read a stratified sample per channel: every message over
sixty words up to 300, and 200 shorter messages taken round-robin across
surfaces in module order until 200 are taken or the surfaces run out.
Each reader returns, in the schema from `human-reply/references/profile-schema.md`:

- shapes per surface: when the shape applies, a skeleton with slots, and
  the person's own messages as examples with names replaced by `<name>`
  and `<team>`: two where the surface has 30 or more records, one
  otherwise
- phrasebook candidates by role (openers, asks, evidence, hedges, pivots,
  closers, visibility, tone markers), one to eight words each, so single
  markers such as "IMO", "JFYI", and "cc:" qualify
- typing habits: contractions, capitalisation, punctuation, code spans
- how disagreement is worded
- sign-off habits

Readers alone miss frequent phrases: a reader proposes what it notices in
a 500-message sample. So before the readers run, `scripts/corpus.py
phrases` lists candidates of three kinds from the whole kept file: word
sequences of one to five words in three or more records (at most 200,
at most 50 single words); the first one to three words of each line in
two or more records (at most 250), which is where discourse markers
such as "Also," "PS:" and greetings sit; and every emoji shortcode and
all-caps word of two to five letters in two or more records. Quoted
lines and code are skipped. Every reader gets the list and places each
candidate that plays a role, leaving out topic words, acronyms of
systems, and filler. The no-Python path
has no list.

Three readers per channel read the same sample. For shapes, disagreement
wording, typing habits, and sign-offs the merge keeps an entry two or more
readers returned. Phrasebook entries are not voted on: a candidate phrase
is kept when `scripts/corpus.py count` finds it, as whole words in
order ignoring case and edge punctuation, in two or more records,
whichever reader returned it, so a rare tone marker that one reader
noticed survives. A reader whose return fails the schema, or has fewer
than two examples for any surface at or above the 30-record floor
(surfaces below the floor need none), is re-run once with a fresh agent; a
second failure marks the channel `partial` in the profile header. When no
reader survives, the channel gets no shapes or phrasebook and is marked
`partial` with that reason.

Cross-channel reconciliation runs over every set-up channel each time a
channel is added or rebuilt. An entry for hedges, typing habits,
disagreement, sign-offs, or the banned list that two or more set-up
channels returned goes into `profile.md`. An entry only some channels
returned goes under the `## Habits` heading of each channel profile that
showed it, and at runtime a channel's Habits override `profile.md` for
that channel. With a single set-up channel every entry goes under that
channel's Habits and `profile.md`'s voice sections stay empty until a
second channel agrees; when a later channel is read, entries already in
`profile.md` that it did not return are demoted to the Habits of the
channels that did.

The colleague sample goes to one reader that returns named traits only
(for example "opens replies with the verdict, no greeting", "uses `>`
quote-reply for multi-part answers"). The person picks which to adopt.
Adopted traits are written into `profile.md` under Borrowed traits as the
person's own, with the colleague's name and the date, and no quoted text.

### 3.7 Calibrate

For each held-out thread, the skill drafts a reply from the thread context
using the just-built profile, then shows the draft beside what the person
actually sent. The person marks what reads wrong in a sentence each. The
marks are written into the channel profile under Calibration notes as
rules ("never open a GitHub reply with a greeting", "DMs to the squad stay
under ten words") and the affected budgets or phrasebook entries are
adjusted. After the adjustments are written, one held-out thread per
channel is re-drafted from the updated profile and shown for a yes or no,
so the last thing the person sees is the profile they will use, and that
re-draft is what acceptance item 2 scores. One round.

When fewer than three held-out threads have a reply by the person after
someone else's message, calibration backfills before giving up. It
searches the channel for the person's pre-cutoff replies older than the
window start, one month at a time for up to 12 months, reads each
candidate thread, and keeps it when a message by someone else comes
before the person's reply, stopping at three. On Slack that is the
collect search with a `before:` no later than the window start, thread
replies only, read with the thread-read tool. On GitHub it is
`gh search prs --commenter` for that month, with review comments read
through `gh api`. On Notion it is the Notion search for pages created that
month, with discussions read through the comments tool. Backfilled threads
are used for calibration only and never written to the corpus. A channel
with no thread that has such a reply after the backfill gets no draft or
re-draft, is marked `partial` with the reason, and does not count towards
item 2. When the person answers no to
the re-draft, the channel is marked `partial` with the reason
`calibration rejected`, so its header reads
`status: partial (calibration rejected)` and `pr-watch` does not draft
from it.

### 3.8 Finish

Before writing, print every shape example per channel in one batch,
numbered; the person strikes or replaces any of them, since the channel
files are permanent and the examples are their own messages. Then write
`profile.md` and `channels/<channel>.md`. Print their paths, the sample
size and window per channel, the drop count, the method, and any channel
marked skipped or partial. Each channel header's `status` line lists every
partial reason recorded during setup, a rejected calibration included.
Delete `corpus/borrow-<channel>.jsonl`
unconditionally, then delete the rest of `corpus/` unless the person says
keep; the keep choice covers the person's own records only and is not
offered when the model did the redaction (section 3.3). Say that
`setup <channel>` rebuilds one channel and `setup` rebuilds all.

## 4. Profile

Both file kinds are markdown with fixed headings so runtime reads them by
section and a person edits them by hand. `human-reply/references/profile-schema.md`
is the normative copy.

### 4.1 profile.md

```
# Voice profile
built: 2026-09-16 | method: measured | channels: slack, github, notion
cutoff: 2026-01 | window: 2025-09..2026-09
inner circle: <names>
borrowed from: <name> (traits listed below)

## Hedges
## Typing habits
## Disagreement
## Sign-offs
## Banned
## Borrowed traits
```

`method` here records the Detect probe from section 3.1. Each channel
file carries its own `method`, which is authoritative for that channel; a
channel that fell back under section 7 changes only its own file.

Hedges: the person's own, with the rule of at most one per message.
Typing habits: the mechanics the person keeps (contractions without
apostrophes in DMs, lowercase first letters on GitHub, spelling kept
correct). Disagreement: the observed pattern (for example first sentence
the disagreement, second the reason, one pivot phrase). Sign-offs: what
closes an ask and what closes a reply. Banned: the person's never-list
plus the humanizer's list by reference. Borrowed traits: one line each,
trait, colleague, date adopted, and that the colleague was told.

### 4.2 channels/<channel>.md

```
# Slack voice
sample: 1,412 messages, 2025-09..2026-09, 61 dropped by the AI filter | method: measured | threshold: 3

## Surfaces
| Surface | Audience | Records | Median | 75th | 90th | Budget | Register |

## Pattern rates
## Phrasebook
## Shapes
## Habits
## Calibration notes
```

Surfaces are fixed per channel by the repo module, so every profile for a
channel has the same rows and runtime never guesses at surface names:

| Channel | Surfaces |
|---|---|
| Slack | inner-circle DM, outer DM, group DM, channel thread reply, channel new post, write-up |
| GitHub | review thread reply, review summary, PR body, issue comment |
| Notion | page comment, inline comment |

Budget is derived from the 90th percentile of pre-cutoff messages (the
whole window when there is no cutoff), rounded up to the nearest ten and
floored at the channel module's minimum for the surface, so a person who
writes long gets a longer budget and a person who writes short is not
padded up to a generic one. The recent window is the drifted period the
skill exists to correct, so it must not set the budget. The per-quarter
series from measure is not absorbed either; the profile reports it as
drift under Pattern rates so the person can see where their recent
messages have grown.

The 30-record floor counts the same population the budget is derived
from: pre-cutoff records per surface, or the whole window when there is
no cutoff. A surface below the floor takes the channel module's default
budget and register and is labelled `estimated` in the Surfaces table,
and every row records its pre-cutoff count beside the budget; the runtime
repeats the label in its first line. On a
profile built by the fallback, the budget derives from the upper bound of
the 90th-percentile bucket, and the table records the bucket beside the
derived budget so a later measured rebuild can be compared against it.

Pattern rates are the measured shares plus the per-quarter drift.
Phrasebook entries carry their count. Shapes carry the person's own
redacted examples. Habits are the channel-specific entries from the
reconciliation rule in section 3.6. Calibration notes are the rules from
section 3.7.

A profile built on the fallback says `method: estimated` in the header
and the runtime repeats that in its first line.

## 5. Runtime

Triggers: `/human-reply`, or prose such as "reply to this thread", "draft
a comment on this PR", "answer this Notion comment", "make this sound like
me", "shorten this". Modes: `draft <what to say>`, `rewrite <text>`,
`audit <text>`.

Workflow per call:

1. Resolve the channel from an explicit argument, a pasted URL
   (`slack.com`, `github.com`, `notion.so`), or the pasted thread. If it
   cannot be settled, ask one question and stop. If the resolved channel
   has no profile file, refuse to draft, say so, and point at
   `setup <channel>`. There is no generic voice.
2. Resolve the surface and budget from the channel module's surface table
   and the profile's numbers. State both, with provenance, in the first
   line before any draft: "Slack, channel thread reply, budget 60 words,
   profile measured 2026-09-16."
3. Pick the shape from the profile's shapes for that surface; the channel
   module names the default when none matches.
4. Write toward the surface median, with the budget as a ceiling a
   message reaches only for content the reader cannot act without, using
   the profile's phrasebook, hedges, typing
   habits, and banned list, and the channel module's markup rules (Slack
   quote lines followed by a blank line, GitHub line-range links at a
   commit and `suggestion` blocks, Notion mention syntax). An in-thread
   reply never restates the thread.
5. Audit against the channel module's checklist plus the profile's
   calibration notes. Fix every hit.
6. If the `humanizer` skill is installed, run the draft through it with
   the instruction in `human-reply/references/humanizer-handoff.md`: it may remove or
   replace words and never add; on any conflict the profile's phrasebook
   wins over the humanizer's defaults. Re-check the budget after.
7. Deliver the draft in a fenced block with the channel's markup as it
   should be pasted, plus where it goes. Nothing else.

`rewrite` keeps every fact, link, and code span of the original and shows
the word count before and after. `audit` lists checklist hits with the
offending line quoted and the count against the budget, and ends pass or
fail, without rewriting.

`allowed-tools` for `SKILL.md`: Read, Bash, Write (setup writes profiles
and corpus files only), Skill, ToolSearch, Agent (setup readers), plus the
connected search tools. No send tool is ever listed.

## 6. pr-watch integration

`pr-watch` posts replies unattended under the person's login. Its
`skills/pr-tooling/pr-watch/references/reply-voice.md` is two things: measured phrasing, and a
posting contract that says what each reply shape must carry (sha,
evidence, pending reason) and what a reply must never say (greetings,
"Great catch", promises of future work, @-mentions of bots, any mention of
tools, agents, automation, or a process).

The change to `pr-watch`, in the same PR series as this skill:

- Cut the trait table, the tier numbers, and the phrasing guidance from
  `reply-voice.md`. Keep the shape contract, the Never list, and the audit
  items that check them. Rename the file `reply-contract.md` and update
  the references in `pr-watch/SKILL.md`, `pr-watch/steps/04-fix-path.md`, and
  `pr-watch/steps/05-rereview.md`.
- The reply step gets one rule: if `human-reply` is installed,
  `~/.claude/human-reply/channels/github.md` exists, and its header says
  neither `partial` nor `estimated`, and the review thread reply row in
  its Surfaces table is not labelled `estimated` (section 4.2), draft
  each reply through `human-reply draft` with channel `github` and the
  shape's required content as the ask, then apply the contract audit. If
  the audit hits, redraft once through `human-reply` with the failing
  items added to the ask as content to include or remove; `human-reply`
  never reads the contract itself. If the second draft still hits, fall
  back to the plain contract-bound reply and note the fallback in the run
  summary. When the profile is absent, partial, or estimated at the
  header or on that surface row, write plainly under the contract; a
  degraded voice is never posted unattended.

Without `human-reply`, `pr-watch` posts correct, contract-bound, plain
replies. With it, the person's voice. Nothing auto-loads one skill under
another; the invocation is explicit in the step.

## 7. Failure handling

Setup:

- Tool not connected for a chosen channel: skip, name it in the summary.
- Fewer than 100 records for a channel after the filter: no profile for
  that channel. Say the sample is too small to measure and offer to widen
  the window or lower the cutoff.
- No pre-cutoff records for a channel: offer to widen the window; if the
  person declines, every surface takes the module default, is labelled
  `estimated`, and the summary says the budgets were not measured.
- Filter drops over 40 percent of a channel's scanned messages after the
  one threshold adjustment: proceed with the filtered set, mark the channel `partial`,
  say why (section 3.4).
- Reader return off-schema or under two examples for a surface at the
  30-record floor: re-run once with a fresh agent; second failure marks
  the channel `partial`.
- Slack search cap: re-window from the last captured date minus one day.
- Python present but `measure.py` fails: show the error and offer the
  fallback for that channel; do not silently switch. The channel file's
  header then says `estimated`; `profile.md` keeps the probe result.
- Setup resumed after the skill changed: setup state records a
  fingerprint of the skill's steps, references, channel modules, and
  scripts. When the fingerprint on resume differs, setup says a resumed
  run would mix files from the old steps with the new ones and recommends
  starting over, then asks as usual.
- Collection interrupted: the person's own JSONL written so far is kept
  and any borrow file is deleted. Collection runs newest first, so
  rerunning `setup <channel>` resumes from the oldest timestamp on disk,
  continuing backwards through the window, and skips records already on
  disk by `ts`. GitHub resumes by repo instead, skipping every repo
  already collected.

Runtime:

- No profile for the resolved channel: refuse and point at setup.
- Channel unresolved: one question, then stop.
- Humanizer grew the draft: trim to budget, re-audit.
- Profile header says `partial` or `estimated`: say so in the first line;
  still draft.

## 8. Privacy

- Redaction runs before the skill writes any record to disk. The session
  transcript Claude Code keeps under `~/.claude/projects/` is outside the
  skill's control and may still hold the raw text the collection tools
  returned; setup says so before collecting. Placeholders replace
  private-key, token, key, password, and connection-string patterns. Those
  patterns are a copy of rules 1 to 12 of
  `pr-loop-lib/references/secret-scan-rules.md` (a copy, not an import,
  because a colleague installs this skill without `pr-loop-lib`), and a
  test fails when the two lists diverge; a new scan rule is added to
  `pr-loop-lib` first and then copied. A separate skill-local list runs
  after the copied rules and covers secrets people paste into messages: a
  `pwd=` URL value (`password`), a `Cookie:` or `Set-Cookie:` header value
  and common session and tracking cookie values (`cookie`), and a Bearer
  token of 20 or more characters (`token`). Each replaces only the value
  and skips one a copied rule already replaced. The redaction
  patterns are tested against synthetic known-bad input, and the
  no-Python path must pass the same fixture before its first write
  (section 3.3).
- `corpus/` is deleted at the end of setup unless the person says keep;
  keep is not offered when the model did the redaction.
- Channel profiles are permanent and carry the person's own messages as
  shape examples, redacted for secrets and with `<name>` and `<team>` in
  place of people, nothing more. The person reviews every example at
  finish (section 3.8) before the file is written.
- Colleague samples are read for traits, and the skill stores them no
  longer than the read step that collects them: the borrow file is
  deleted there, again at the end of setup, and on any interrupted run,
  regardless of the keep choice. The session transcript is the exception
  named above, and the consent question says so. The collector runs only
  after the person confirms the colleague has been told. The profile
  records the trait, the colleague's name, and that confirmation, no
  quoted text.
- Profiles live in the home folder only. The repo never holds a profile,
  and the deletion of `slack-reply` removes the one set of per-person
  numbers the repo currently holds.
- Nothing in a profile or draft mentions tools, agents, or automation.

## 9. Testing and acceptance

Tests live under `skill-tests/human-reply/` and follow the existing pytest
layout.

- `measure.py`: word counting collapses links and code to one token; per-
  surface percentiles on a fixture with known answers; pattern rates;
  quarter drift; the long-message list; the surface budget derivation.
- `redact.py`: every pattern against synthetic known-bad input, a
  known-clean fixture that must pass untouched, and an assertion that the
  copied pattern list matches rules 1 to 12 of
  `pr-loop-lib/references/secret-scan-rules.md`; the skill-local patterns
  each have a known-bad case in the same fixture.
- AI filter: a Slack fixture of paired messages, the 2025 originals and
  their 2026 scaffolded versions from the current `slack-reply` shapes
  file, asserting each side lands where it should at the default
  threshold; plus a GitHub and a Notion fixture of paired native-form and
  scaffolded PR bodies, review summaries, and page comments, asserting
  that headers, labelled bullets, and a closing summary do not score on
  those surfaces while the shared tells still do.
- Corpus record schema: every collector's output validates against
  `human-reply/references/corpus-record.md`; the hold-out marker excludes records
  from measure.
- `scripts/validate.py` unchanged; it discovers the new skill root and
  checks every `setup/`, `channels/`, and `references/` link resolves.

Acceptance, recorded in the PR that ships the skill:

1. Extractor regression: setup run on the author's own Slack, and the
   generated `channels/slack.md` compared by hand against the current
   `slack-reply` numbers and phrasebook, on the tiers the hand corpus
   notes measure, on each tier with 30 or more records in the sample
   (below that floor setup labels the tier estimated). Pass when every
   median is within five words of the
   hand-derived one, every 90th percentile is within 10 percent of it,
   and every hand phrasebook entry that appears in two or more records of
   the sample is in the generated phrasebook. Budgets are not compared:
   the hand budgets were judgment calls, while setup derives them from
   the 90th percentile by a fixed rule.
2. Second person: one colleague runs setup end to end on their own machine
   for at least one channel, and the calibration round is the test. Pass
   when the person accepts the post-adjustment re-draft (section 3.7) for
   every channel they set up that ran calibration; at least one channel
   must have.

Version one is not done until both pass.

## 11. Decisions

Recorded so they are not re-litigated in the plan.

- Text only in version one. Posting is a later addition once drafts are
  trusted.
- Guided setup with one calibration round, not unattended and not
  iterative. Some facts (inner circle, cutoff, borrowed traits) cannot be
  extracted from messages, and one round against held-out threads is the
  only way a colleague can tell the profile is theirs.
- Measured numbers when Python is present and a surface has 30 or more
  records, model estimates or module defaults otherwise, with the cost
  stated and the method labelled in the profile and on the surface row.
  The fallback shares every step except measure.
- Colleague influence is a one-time construction. Adopted traits are the
  person's voice from then on and are not attributed at runtime.
- `slack-reply` is replaced, not wrapped. Its platform facts move into
  the Slack channel module; its person facts leave the repo.
- `pr-watch` keeps its posting contract and Never list and loses its
  phrasing guidance. It invokes `human-reply` explicitly when installed.
- The AI filter is a cutoff date plus a rule-based scaffolding-pattern
  score on long messages (section 3.4), not a machine-learning
  AI-detection classifier judging every message. Short messages are
  almost never AI-written, and the scan targets the structures the
  author's own corpus showed as the tell, listed per channel because the
  tells differ by platform.

## Deferred / Open Questions

### From 2026-09-16 review

- **Thirty-minute setup goal ignores Slack's context-only collection** — 1. Goals and non-goals / 3.3 Collect (P1, feasibility, confidence 75)

  Setup will very likely blow past the stated thirty-minute target for
  anyone whose connected channel is Slack: the Slack MCP has no API token
  and returns results only into the model's context, so nothing writes a
  Slack record to disk except the model itself, unlike GitHub's
  `gh api` path. Collecting up to 1,500 records across month-windowed,
  20-page-capped searches means dozens of search round trips plus
  per-record redaction and writes performed by the model in real time, an
  order of magnitude slower than the CLI-piped GitHub collector the same
  goal is implicitly modeled on. The goal statement in section 1 and the
  cap in 3.3 are not reconciled anywhere in the document.
