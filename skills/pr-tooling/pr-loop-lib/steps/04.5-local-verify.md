# Loop step 04.5 — Local verify (build + test)

Runs BEFORE staging/pushing any fixer changes. Goal: no broken commit ever
reaches the remote.

## Worktree root

Every command below runs with the worktree root as its working directory:
the `{{WORKTREE_ROOT}}` the caller passed to `steps/04-dispatch-fixers.md`,
or the current working directory when it passed none. Detection reads
files in the root. Set the working directory inside the command that runs
(`cd <root> && <command>`), because it does not carry to the next call.
Read every `git` command as `git -C {{WORKTREE_ROOT}} ...`. The retry
subagent gets the same `{{WORKTREE_ROOT}}`.

## Skip conditions

- The step's file list is empty (no code changes to verify). Proceed
  directly to step 06 which will also skip.

The **file list** is `context.files_changed_this_iteration`, or the list
the caller passes when it runs this step outside the comment loop, where
that field stays empty: pr-autopilot step 03.5 D3 passes the union of
its dispatch's `files_changed`, step 03's auto-implement and
`10-ci-failure-classify.md` pass their fixer's. Every rule below that
names the file list (the baseline, the retry, the rollback) reads that
list, and a retry subagent's files are added to it.

## Command detection

Any step that runs this file's detected test command directly instead of
invoking this step (pr-autopilot step 01.5 and step 04's text-fix
verify, pr-watch's base update) applies "Local suites" to it as well.

First hit wins:

1. `CLAUDE.md` or `AGENTS.md` in the worktree root contains a `Build & Test`
   section with explicit commands → use those verbatim.
2. `*.sln` present → build: `dotnet build <sln>`; test: `dotnet test <sln>`.
3. `package.json` present → build: `npm run build` (only if the script
   exists in package.json); test: `npm test`.
4. `Cargo.toml` present → build: `cargo build`; test: `cargo test`.
5. `go.mod` present → build: `go build ./...`; test: `go test ./...`.
6. `Makefile` → if targets `build` and `test` exist: `make build && make test`.
7. `justfile` → `just build test` if both recipes exist.
8. `Taskfile.yml` → `task build test` if both tasks exist.
9. `pyproject.toml` or `setup.py` → test: `pytest` (build step skipped).
10. None of the above → skip verify. Log
    `"no build/test commands detected; relying on CI for validation"`.

## Local suites

The test command runs only suites that can pass on this machine.

1. The repo's own local or unit test command, filter, category, script or
   target wins and is used verbatim: one named in `CLAUDE.md`, `AGENTS.md`,
   `CONTRIBUTING.md` or `README.md`, a `Makefile`/`justfile`/`Taskfile.yml`
   target (`test-unit`, `test:unit`, `unit`), a `package.json` script
   (`test:unit`), or a `.runsettings` or test filter file the repo
   documents. This fits Command detection rule 1: when the repo's
   documented command is itself a local or unit command, it is both; when
   the repo documents only a run-everything command, rule 2 below filters
   it.
2. Leaving a suite out needs evidence that it needs a deployed
   environment, never its name alone. List the test suites (.NET: the test
   projects in the solution; others: the top-level test directories or
   packages). Split the project or directory name (never the absolute
   path) on `.`, `-` and `_`. A suite is a candidate when one of those
   parts is, case-sensitively, one of `Contract`, `E2E`, `EndToEnd`,
   `Integration`, `Smoke`, `Acceptance`, `Live`, `Functional`, or one of
   them followed by `Test` or `Tests`. Leave a candidate out only when its own
   config or fixture code reads a base URL, credential or secret for a
   remote host from the environment or a settings file, or the repo's docs
   say it needs a deployed environment. A candidate with no such evidence
   runs. (`Contracts` is not the word `Contract`; an in-process
   integration suite runs.)
3. A suite already in `context.verify_excluded_suites` from an earlier
   iteration of this run stays out without being re-tried.
4. Run the remaining suites one command at a time (`dotnet test <project>`
   per project instead of `dotnet test <sln>`; the equivalent per-package
   form elsewhere). For .NET, after the solution build of this step has
   just succeeded in the same configuration, pass `--no-build` to each
   per-project `dotnet test`. Build still covers the whole solution.
5. Store each left-out suite in `context.verify_excluded_suites` as
   `{suite, reason}`, one entry per suite across iterations, and log
   `verify_suites_excluded {suites}`. Step 11 reports them as not run
   locally, never as passed.
6. With every suite left out, skip the test run, log it, and set
   `context.verify_tests_ran[<iteration>] = false`; otherwise set it to
   `true`. Build still runs. An iteration with no test run is reported as
   "build only", never as tests green.

## Execution rules (hard requirements)

From the user's global CLAUDE.md:
- Sequential only — never run multiple build/test commands in parallel.
- Foreground only — never `run_in_background`.
- Timeout >= 300000ms (5 min). Raise to the value declared in CLAUDE.md if
  higher.
- Before starting, kill any lingering process of the same toolchain
  (`dotnet build-server shutdown`, or equivalent).
- Never use `--no-verify` on commits downstream.
- Capture full stdout + stderr for failure analysis.

## On failure

A failing test is set aside only when it fails the same way without this
iteration's fixes. Its output text alone never decides that.

1. The fixes are already committed: no file in the file list differs
   from `HEAD` (`git status --porcelain -- <files>` prints nothing).
   This is the pr-watch re-run after its commit and base merge. Every
   failure, a build failure included, is real: the caller gets the
   failure, no retry subagent is dispatched, and nothing is rolled back
   by this step. `context.unit_bases` being empty or not does not decide
   this.
2. A build failure (fixes not committed) is never set aside and gets no
   baseline: the ladder below applies.
3. A test failure with a wave base in `context.unit_bases`: run one
   baseline per run of this step, in place (the working tree has the
   restored packages, ignored config and build output a fresh checkout
   lacks):
   a. Snapshot the fixed tree with the "Unit base" snapshot command of
      `04-dispatch-fixers.md`; store the id in
      `context.verify_baseline_tree` and write state.
   b. Put the pre-fix content back: run "Rollback" of
      `04-dispatch-fixers.md` for every file in the file list against
      the wave base. This restore is temporary: it changes no verdict
      and logs no `rollback_deleted`, and a file that procedure would
      leave in place stays as it is for the baseline.
   c. Re-run only the suites that failed (rebuild first), same execution
      rules.
   d. Put the fixes back: restore each of the same files from
      `context.verify_baseline_tree` with
      `git restore --source=<tree> --worktree -- <file>`; a file that
      tree does not hold was deleted by its fix and is deleted again. Set
      `context.verify_baseline_tree = null`, write state, log
      `verify_baseline {failing_before, failing_after_baseline, tree}`.
   e. A test that failed in (c) with the same error as before: not caused
      by the fixes. Record a suite whose every failure is of this kind and
      whose error is a refused or timed-out connection, a DNS failure, a
      401/403/5xx from a remote host or a missing environment variable,
      secret or config value in `context.verify_excluded_suites` (reason:
      the error seen); record other such tests in
      `context.verify_preexisting_failures`. Log
      `verify_suites_excluded {suites}`. These do not count.
   f. A test that passed in (c), failed differently, or does not exist
      without the fixes: caused by the fixes. The ladder below applies.
4. A test failure with no wave base (a caller dispatched a fixer without
   recording a unit base): no baseline is possible; every failure is
   real and the ladder applies.
5. At step start, a non-null `context.verify_baseline_tree` means the
   pre-fix content may still be on disk. The file list of that run is
   not known any more, so put the whole fixed tree back:
   `git restore --source=<tree> --worktree -- :/` (the tree is a
   snapshot of the whole working tree, so every file it holds returns to
   its fixed content), then set the field to null.
6. If after (e) no failure is left, the step succeeds.

**First failure in this iteration**:
1. Dispatch a retry subagent with `subagent_type: "pr-fixer"` and
   `model: "sonnet"`, both passed explicitly; where `pr-fixer` is not
   installed, `subagent_type: "general-purpose"` with the same model. It
   does not build or test; the orchestrator re-runs the commands. The files
   it changes are added to the file list. Its
   prompt is the same fixer-prompt concatenation as step 04, but with:
   - Feedback-body replaced by the build/test failure output.
   - `{{FILE_PATH}}` set to each file in the file list
     (listed as candidates).
   - Task description: "The changes made in response to the previous
     feedback broke the local build or tests. The failure output is quoted
     below. Reconcile by adjusting the changes to keep the original
     feedback addressed while making the build/tests pass. Do not revert
     the feedback fix unless absolutely necessary and document why in your
     reason."
2. After the retry subagent returns, re-run the build/test commands. A
   test already in `context.verify_preexisting_failures`, or in a suite
   already in `context.verify_excluded_suites`, is set aside again
   without a new baseline. Only other failures make it the second
   failure. (A suite in `verify_excluded_suites` is in fact not re-run,
   per "Local suites" rule 3.)

**Second failure in this iteration (retry didn't fix it)**:
1. Roll back with the "Rollback" procedure of `04-dispatch-fixers.md`
   for every file in the file list against the wave base (one base for
   the wave: no order between units, and files only the retry subagent
   edited are covered). Scoped strictly to files this iteration
   modified; never touch earlier iterations. When there is no wave base,
   nothing can be restored: leave the files, set the affected returns to
   `needs-human` with reason "local verify failed twice and there is no
   base to roll back to", and tell the caller.
2. For each agent in `context.agent_returns` whose `files_changed` list
   overlaps the rolled-back set, change its verdict to `needs-human` and
   append the build/test failure summary to its `reason`. For each such
   return also set `build_rollback: true` on its
   `context.verifier_judgements` entry.
3. Clear `context.files_changed_this_iteration` to empty, and tell a
   caller that passed its own list that every file in it was rolled back.
4. Proceed to step 06 — step 06 will see no files to stage and skip commit.
   Step 07 will still post replies for all items.

## On success

Record `context.sanity_check_passed[iteration] = true` for the final report.
Proceed to step 06.
