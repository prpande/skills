# Loop step 04.5 — Local verify (build + test)

Runs BEFORE staging/pushing any fixer changes. Goal: no broken commit ever
reaches the remote.

## Worktree root

Every command below runs with the worktree root as its working directory:
the `{{WORKTREE_ROOT}}` the caller passed to `steps/04-dispatch-fixers.md`,
or the current working directory when it passed none. Detection reads
files in the root. Set the working directory inside the command that runs
(`cd <root> && <command>`), because it does not carry to the next call.
Read every `git` command as `git -C {{WORKTREE_ROOT}} ...`. The retry
subagent gets the same `{{WORKTREE_ROOT}}`.

## Skip conditions

- The step's file list is empty (no code changes to verify). Proceed
  directly to step 06 which will also skip.

The **file list** is `context.files_changed_this_iteration`, or the list
the caller passes when it runs this step outside the comment loop, where
that field stays empty: pr-autopilot step 03.5 D3 passes the union of
its dispatch's `files_changed`, step 03's auto-implement and
`10-ci-failure-classify.md` pass their fixer's. Every rule below that
names the file list (the baseline, the retry, the rollback) reads that
list, and a retry subagent's files are added to it.

## Interrupted baseline

Before anything else in this step, a non-null
`context.verify_baseline_tree` means an earlier baseline run ("On
failure" rule 3, "Blame" step 3) or halving round ("Blame" step 4) was
interrupted and the pre-fix content may still be on
disk. Put the fixed content back for the files of that run only, which
`context.verify_baseline_files` holds: restore each from the tree with
`git restore --source=<tree> --worktree -- <file>` (a file the tree
does not hold is deleted), then set the tree to null and the list to
`[]` and write state. No other path is touched.

## Command detection

Any step that runs this file's detected test command directly instead of
invoking this step (pr-autopilot step 01.5 and step 04's text-fix
verify, pr-watch's base update) applies "Local suites" to it as well.

First hit wins:

1. `CLAUDE.md` or `AGENTS.md` in the worktree root contains a `Build & Test`
   section with explicit commands → use those verbatim.
2. `*.sln` present → build: `dotnet build <sln>`; test: `dotnet test <sln>`.
3. `package.json` present → build: `npm run build` (only if the script
   exists in package.json); test: `npm test`.
4. `Cargo.toml` present → build: `cargo build`; test: `cargo test`.
5. `go.mod` present → build: `go build ./...`; test: `go test ./...`.
6. `Makefile` → if targets `build` and `test` exist: `make build && make test`.
7. `justfile` → `just build test` if both recipes exist.
8. `Taskfile.yml` → `task build test` if both tasks exist.
9. `pyproject.toml` or `setup.py` → test: `pytest` (build step skipped).
10. None of the above → skip verify. Log
    `"no build/test commands detected; relying on CI for validation"`.

## Local suites

The test command runs only suites that can pass on this machine.

1. The repo's own local or unit test command, filter, category, script or
   target wins and is used verbatim: one named in `CLAUDE.md`, `AGENTS.md`,
   `CONTRIBUTING.md` or `README.md`, a `Makefile`/`justfile`/`Taskfile.yml`
   target (`test-unit`, `test:unit`, `unit`), a `package.json` script
   (`test:unit`), or a `.runsettings` or test filter file the repo
   documents. This fits Command detection rule 1: when the repo's
   documented command is itself a local or unit command, it is both; when
   the repo documents only a run-everything command, rule 2 below filters
   it.
2. Leaving a suite out needs evidence that it needs a deployed
   environment, never its name alone. List the test suites (.NET: the test
   projects in the solution; others: the top-level test directories or
   packages). Split the project or directory name (never the absolute
   path) on `.`, `-` and `_`. A suite is a candidate when one of those
   parts is, case-sensitively, one of `Contract`, `E2E`, `EndToEnd`,
   `Integration`, `Smoke`, `Acceptance`, `Live`, `Functional`, or one of
   them followed by `Test` or `Tests`. Leave a candidate out only when its own
   config or fixture code reads a base URL, credential or secret for a
   remote host from the environment or a settings file, or the repo's docs
   say it needs a deployed environment. A candidate with no such evidence
   runs. (`Contracts` is not the word `Contract`; an in-process
   integration suite runs.)
3. A suite already in `context.verify_excluded_suites` from an earlier
   iteration of this run stays out without being re-tried.
4. Run the remaining suites one command at a time (`dotnet test <project>`
   per project instead of `dotnet test <sln>`; the equivalent per-package
   form elsewhere). For .NET, after the solution build of this step has
   just succeeded in the same configuration, pass `--no-build` to each
   per-project `dotnet test`. Build still covers the whole solution.
5. Store each left-out suite in `context.verify_excluded_suites` as
   `{suite, reason}`, one entry per suite across iterations, and log
   `verify_suites_excluded {suites}`. Step 11 reports them as not run
   locally, never as passed.
6. With every suite left out, skip the test run, log it, and set
   `context.verify_tests_ran[<iteration>] = false`; otherwise set it to
   `true`. Build still runs. An iteration with no test run is reported as
   "build only", never as tests green.

## Execution rules (hard requirements)

From the user's global CLAUDE.md:
- Sequential only — never run multiple build/test commands in parallel.
- Foreground only — never `run_in_background`.
- Timeout >= 300000ms (5 min). Raise to the value declared in CLAUDE.md if
  higher.
- Before starting, kill any lingering process of the same toolchain
  (`dotnet build-server shutdown`, or equivalent).
- Never use `--no-verify` on commits downstream.
- Capture full stdout + stderr for failure analysis.

## On failure

A failing test is set aside only when it fails the same way without this
iteration's fixes. Its output text alone never decides that.

1. The fixes are already committed: no file in the file list differs
   from `HEAD` (`git status --porcelain -- <files>` prints nothing).
   This is the pr-watch re-run after its commit and base merge. Every
   failure, a build failure included, is real: the caller gets the
   failure, no retry subagent is dispatched, and nothing is rolled back
   by this step. `context.unit_bases` being empty or not does not decide
   this.
2. A build failure (fixes not committed) is never set aside here and
   gets no baseline: the ladder below applies, and only its "Blame"
   step 3 may run one.
3. A test failure with a wave base in `context.unit_bases`, where some
   failing test is not a target test the caller passed (a failure made
   only of target tests gets no baseline, since none can be set aside:
   the ladder applies): run the
   baseline once here, in place (the working tree has the
   restored packages, ignored config and build output a fresh checkout
   lacks):
   a. Snapshot the fixed tree with the "Unit base" snapshot command of
      `04-dispatch-fixers.md`; store the id in
      `context.verify_baseline_tree`, and store in
      `context.verify_baseline_files` the files of the file list
      that (b) will replace: those "Rollback" restores or deletes,
      never one its case 2 or 3 leaves in place. Write state. When the
      snapshot fails twice (no tree id, or a non-zero exit), nothing is
      restored: no baseline is run, every failure is real and the ladder
      applies.
   b. Put the pre-fix content back: run "Rollback" of
      `04-dispatch-fixers.md` for every file in the file list against
      the wave base. This restore is temporary: it changes no verdict
      and logs no `rollback_deleted`, and a file that procedure would
      leave in place stays as it is for the baseline. When any file
      was left in place ("Rollback" case 2 or 3), the tree under test
      still holds part of the fixes: (c) and (d) run, but (e) sets
      nothing aside and every failure goes to the ladder.
   c. Re-run only the suites that failed (rebuild first), same execution
      rules.
   d. Put the fixes back: restore each file in
      `context.verify_baseline_files` from
      `context.verify_baseline_tree` with
      `git restore --source=<tree> --worktree -- <file>`; a file that
      tree does not hold was deleted by its fix and is deleted again. Set
      `context.verify_baseline_tree = null` and
      `context.verify_baseline_files = []`, write state, log
      `verify_baseline {failing_before, failing_after_baseline, tree}`.
   e. A test that failed in (c) with the same error as before: not caused
      by the fixes. Record a suite whose every failure is of this kind and
      whose error is a refused or timed-out connection, a DNS failure, a
      401/403/5xx from a remote host or a missing environment variable,
      secret or config value in `context.verify_excluded_suites` (reason:
      the error seen); record other such tests in
      `context.verify_preexisting_failures` as `{test, error}`. Log
      `verify_suites_excluded {suites}`. These do not count. A test
      the caller passed as a target test (`10-ci-failure-classify.md`
      passes the tests that failed in CI) is never set aside here: its
      failure goes to the ladder.
   f. A test that passed in (c), failed differently, or does not exist
      without the fixes: caused by the fixes. The ladder below applies.
4. A test failure with no wave base (a caller dispatched a fixer without
   recording a unit base): no baseline is possible; every failure is
   real and the ladder applies.
5. If after (e) no failure is left, the step succeeds.

Below, "the ladder" is "Retries" and then "Blame". A failure that is not
set aside is either a **build failure** or a **test failure**, and the
two kinds are counted apart.

### Retries

Each kind gets one retry subagent per run of this step:
`context.verify_retries_used` is `{build: false, test: false}` until a
retry is used, and the kind's flag is set and state written when its
retry is dispatched, or when its unit base cannot be recorded (rule 1).
A resumed step keeps the flags; they are reset to `{build: false,
test: false}` when the step ends, however it ends. The first build failure dispatches the build retry. When the build then
passes and tests fail, the test failures get their own retry, whatever
the build retry did.

1. Record a unit base for the retry ("Unit base" of
   `04-dispatch-fixers.md`) under the key `verify-retry-<kind>`, with
   `unit` the same key and `order` one above the highest in
   `context.unit_bases`; with no wave base there is none to record. When
   that snapshot fails twice, the retry has no items to mark
   `needs-human`: dispatch no retry, set the kind's flag, and send the
   failure to "Blame". Otherwise dispatch a retry subagent with `subagent_type: "pr-fixer"` and
   `model: "sonnet"`, both passed explicitly; where `pr-fixer` is not
   installed, `subagent_type: "general-purpose"` with the same model,
   under the "Time limits" of `04-dispatch-fixers.md`. It does not build
   or test; the orchestrator re-runs the commands. The files it changes
   are added to the file list and stored as `files` on its
   `context.unit_bases` entry; they are the files of its unit. A retry
   that times out is rolled back as that section says, and the failure
   that sent it goes to "Blame". Its
   prompt is the same fixer-prompt concatenation as step 04, but with:
   - Feedback-body replaced by the build/test failure output.
   - `{{FILE_PATH}}` set to each file in the file list
     (listed as candidates).
   - Task description: "The changes made in response to the previous
     feedback broke the local build or tests. The failure output is quoted
     below. Reconcile by adjusting the changes to keep the original
     feedback addressed while making the build/tests pass. Do not revert
     the feedback fix unless absolutely necessary and document why in your
     reason."
2. After the retry subagent returns, re-run the build/test commands. A
   test that this run's baseline (rule 3e) recorded in
   `context.verify_preexisting_failures` and that fails with the error
   recorded there is set aside again without a new baseline. An entry
   from an earlier wave or iteration sets nothing aside, a different
   error counts, and a test the caller passed as a target test always
   counts. A failure not set aside goes to its kind's retry when that
   is still unused, else to "Blame". (A suite in
   `verify_excluded_suites` is in fact not re-run, per "Local suites"
   rule 3.)

### Blame

Runs for a kind whose retry is used and still fails. It rolls back only
units the failure can be pinned on, and never a verified fix from a unit
it cannot be pinned on. Every unit rolled back here goes through "Unit
rollback" of `04-dispatch-fixers.md` with the reason "local verify:
<first line of the failure>". A **suspect** is a unit of this run whose
files are still in the file list, the retry units included.

With no wave base nothing can be restored: leave the files, set the
affected returns to `needs-human` with reason "local verify failed and
there is no base to roll back to", tell the caller, and stop here.

1. **Flaky check** (test failures). Re-run only the failing tests that
   are not target tests (rule 3e) once, on the tree as it stands (a
   filter that names them: `dotnet test --filter`, pytest node ids, or
   the runner's equivalent). A test passes only when the run's report
   lists it as executed and passed; a run that matched or executed no
   test, or does not list the test by name, is not a pass. A test that
   passes is flaky: it does not count, nothing is rolled back for it,
   and it goes into `context.verify_flaky_tests` as `{test, units}`,
   `units` being the suspects whose files hold the test's source file or
   the file it covers by name (`FooTests.cs` covers `Foo.cs`). Log
   `verify_flaky {tests}`. This run does not count toward the halving
   limit in 4. A target test (rule 3e) is never set aside as flaky, and
   in step 3 never as pre-existing.
2. **Pin by file.** A build failure first gets its baseline as step 3
   below describes, before anything is rolled back here; a pre-existing one
   ends the step there. A failure's files are the failing test's source
   file or the file a build error names, taken as a repo-relative path
   with forward slashes (an absolute or backslashed path in the output is
   made relative to the repository root, and compared without regard to
   case on Windows). Paths that only appear in stack frames pin nothing.
   Roll back every suspect whose files include one of them. A test that only
   the fix round added sits in the file of the unit that added it, so
   that unit is rolled back whole and the failure reaches no other unit.
   When anything was rolled back, do a **full re-run** once: rebuild and
   run the build and every local suite ("Local suites"), not only the
   ones that failed, since the tree that gets pushed has never been
   tested whole. This run is outside the limit in 4 too, and when it
   passes the step succeeds. A failure it shows goes on to 3 to 5.
3. **Baseline.** A failure still left that no suspect's files hold, or
   that survived 2, gets a baseline when it has none yet from rule 3 or
   from step 2:
   run rule 3 (a) to (d) for the suspects' files, re-running only that
   failure (the build alone for a build failure). One that fails the
   same way without the fixes is pre-existing: roll nothing back and
   keep every fix. A test is recorded as rule 3e says. A build failure is
   one item in `context.needs_human_items` with the reason "the build
   fails without the fixes too: <error>"; set
   `context.verify_tests_ran[<iteration>] = false`, record
   `context.sanity_check_passed[iteration] = false`, and end the step.
4. **Halve.** A failure left now passes without the fixes, yet no unit's
   files hold it. Group the suspects into blocks: units that share a
   file are one block, since one cannot be restored without the other.
   Snapshot the fixed tree into `context.verify_baseline_tree` and write
   state. When the snapshot fails twice, restore nothing, do not halve,
   and roll back the units of every suspect block. Before each round's
   restore, add that round's files to `context.verify_baseline_files`
   and write state, so "Interrupted baseline" can put them back. Then, at
   most 3 times while more than one block is suspect:
   a. Split the suspect blocks in dispatch order into a first half A
      (one more when the count is odd) and a second half B.
   b. Restore B's files temporarily, each against the base of the
      lowest-`order` unit of its block, as rule 3b restores; rebuild and
      re-run only the failing suites (or the build).
   c. The round is conclusive only when every restore succeeded, none
      of them stopped at "Rollback" case 2 or 3 (those leave a file in
      place with its fix), and the run shows either
      the same failure or no failure. Same failure: B is cleared and A
      stays suspect. Passing: A is cleared and B stays suspect. Any other
      result (a restore that failed or left a file in place, or a
      different build or test failure) is inconclusive: clear neither
      half, put the files back, and stop halving. Put every temporarily
      restored file back from the snapshot before the next round; a file
      the snapshot does not hold is deleted again.
   Log `verify_bisect {round, suspects, cleared, result}` per round.
   Then put every file back from the snapshot the same way, set the tree
   to null and the list to `[]`, write state, and roll back the units of
   the blocks still suspect.
5. **Confirm.** After the rollback in 4, do the full re-run of 2 (2
   already did it after its own rollback). A suite that the last
   halving round ran and passed on the tree now on disk (that round
   passed, and its restored block is the one rolled back) is not run
   again. When it still fails, roll back every suspect that is
   left, with the reason "local verify still failed after the failing
   units were rolled back; it could not be pinned on fewer units". That
   is the only case where units the failure was not pinned on are rolled
   back.

When the step ends with no failure left (every failure set aside as
flaky or pre-existing, or the last run passed), run "On success". Any
other end records `context.sanity_check_passed[iteration] = false`.

Then proceed to step 06, which stages only the files left in
`context.files_changed_this_iteration`, and tell a caller that passed
its own list which of its files were rolled back. Step 07 still posts
replies for all items.

## On success

Record `context.sanity_check_passed[iteration] = true` for the final report.
Proceed to step 06.
