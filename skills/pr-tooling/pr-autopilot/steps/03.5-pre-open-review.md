# Step 03.5 — Pre-open review

Every review runs before the PR exists, so a finding is fixed or
declared before any human or bot sees the code. This step commits the
work locally, runs the host's `/code-review` at `max` and the step 02
lens agents at the same time, fixes or declares every finding from both
in one round, reviews those fixes, and writes the kept decisions into
commit messages. Nothing is pushed here; step 04 pushes and opens the PR.

`pr-followup` never runs this step.

## Dry-run

`--dry-run` runs every review in this step, so a dry run tests the same
flow a real run uses. It commits nothing, pushes nothing and posts
nothing; the fixes stay in the working tree. Each part says what changes:

- **A** runs its secret scan and writes the commit message to the
  dry-run directory without committing.
- **B** runs `/code-review max` and the lens agents over the working
  tree ("Launch").
- **C** is unchanged.
- **D** fixes in the working tree and writes its commit message to the
  dry-run directory. Fixers, verifiers and rollbacks work as in a real
  run (`04-dispatch-fixers.md` "Unit base" and "Rollback"). Where E in a
  real run reads commits, a dry run reads the snapshot trees D2 and D5
  take, each written without a commit, a ref, or a change to the
  index:
  ```bash
  idx="$(git rev-parse --absolute-git-dir)/pr-autopilot-snapshot-index"
  rm -f "$idx" "$idx.lock"
  cp "$(git rev-parse --absolute-git-dir)/index" "$idx" &&
    GIT_INDEX_FILE="$idx" git add -A -- <paths> && GIT_INDEX_FILE="$idx" git write-tree
  echo "exit=$?"; rm -f "$idx"
  ```
  `<paths>` is what a real run would have committed by then: the paths
  A stages, plus every file a fixer of this step has changed, that
  exists on disk or is in the index (`git ls-files --error-unmatch --
  <file>` succeeds); a file a rollback deleted is left out. A tracked
  file outside that list stays as the index holds it (its committed
  content unless the user staged it), and an untracked one stays out.
  With no such path, leave the `git add` out. It prints a tree id that `git diff <tree> <tree>`, `git diff <tree>`
  and `git show <tree>:<path>` accept, then `exit=0`. `.pr-autopilot/`
  is ignored, so it is never in a snapshot. An empty tree id or a
  non-zero exit is a failure: take the snapshot once more, and on a
  second failure log `error {stage: "dry-run-snapshot"}`, set
  `context.fix_round_skipped_reason` to "snapshot failed", skip E, and
  write "Fix-round review did not run: snapshot failed" in the review
  summary and the step 11 report, never as a clean review. A failed
  snapshot stops only E: D's fixers still run, and D5 takes no head tree
  after a failed D2 snapshot.
- **E** reviews the diff between the snapshot taken before D's fixers
  and the one taken after them.
- **F** builds the declarations and writes the "Kept on purpose" message
  to the dry-run directory.

## A — Commit the work locally

1. **Secret scan (BLOCKING).** Apply
   `pr-loop-lib/references/secret-scan-rules.md` to every file about to
   be staged:
   - `context.uncommitted` (the "related" subset from step 01)
   - `context.spec_updates` files (step 03)
   - source files the step 03 auto-implement fixers changed, which step 03
     added to `context.uncommitted`; stage them **unconditionally**, never
     re-filtered for relatedness
   - `context.simplify_files` (folded `/simplify` edits from step 01.5,
     staged **unconditionally**, never re-filtered for relatedness)

   Any match → halt with the BLOCK message from the secret-scan
   reference. Do not stage.
2. Stage exactly those paths with `git add <specific paths>`. Never
   `git add .` or `git add -A`. When nothing is staged (all work was
   already committed), skip to 4.
3. Commit-message convention: `CONTRIBUTING.md` guidance if present,
   else the pattern of the last 20 commits on the base branch (`feat:`,
   `fix:`, ...), else a short imperative subject about the "why".
   Subject from `context.what_was_built` plus the dominant change
   category. Body: one paragraph pointing to the motivating spec files,
   if any.
   ```bash
   git commit -F <message file>
   ```
   Commit signing follows the user's git config. Never pass
   `--no-verify`, `--no-gpg-sign` or `-c commit.gpgsign=false`; surface a
   signing failure instead. Every commit in this step (A, D5, F) first
   applies the main-branch guard of `pr-loop-lib/steps/06-commit-push.md`
   and afterwards emits its `git_commit_argv` audit event; none pushes.
4. Set `context.head_sha` to `git rev-parse HEAD`.

## B — `/code-review` at max, with the lens agents beside it

### Settled decisions

Reset `context.internal_review_findings`,
`context.preflight_minor_findings`, `context.code_review_dismissed` and
`context.needs_human_items`, `context.verify_excluded_suites` and
`context.verify_preexisting_failures` to `[]`, and `context.fix_round_base_sha`,
`context.fix_round_head_tree` and `context.fix_round_skipped_reason` to
null, so a state file loaded from an earlier run contributes nothing.

Before either review starts, delete any existing
`<repo-root>/.pr-autopilot/branch-<slug>-settled.md`, then write the
decisions this run has, so neither review re-argues them. The rule
every reviewer gets is
`pr-loop-lib/references/adversarial-review-prompt.md` "Settled
decisions": a ruling stands, and what it costs a caller is still
reported, as "declared but risky". Sources:

- every line of a "Kept on purpose:" block in the commit messages of
  `git log <base_sha>..HEAD` (a re-run after a halt keeps what the last
  run decided)
- the declarations section F builds from `context.spec_alignment_notes`,
  the context map's "Declared differences" and the scope sources

Write them as `- <statement> (<file>:<line>)` lines to that file, under
this first line, so a reviewer that reads only the file still gets the
rule:

```
Settled: do not argue for a different choice. When the code no longer matches an item, report that as an ordinary finding. When the code as stated can crash a client, hide an outage or failure, or drop the caller's own data, report it with a summary that starts "Declared but risky: " followed by the item's opening words.
```

When there are none, write no file; `<settled hint>` below is then empty
and the lens prompts get "none".

### Launch

Before launching: when `context.code_review_status` is `"running"` and
`context.code_review_invoked_head` equals `context.head_sha` (a re-run
after a halt or an interruption, same head), do not launch again; go to
"Wait for the result". When the head differs, the earlier review is
stale and a new launch is made. Every launch sets
`context.code_review_invoked_head = context.head_sha` and logs
`code_review_invoked` with `head_sha` and `launch`.

Only the result of the newest launch is parsed. A result names the
branch head it reviewed in its first lines. A result is stale only when
it names a head that is not `context.code_review_invoked_head`, or when
the host shows it came from an older launch's task while the newest
launch is still running; save it beside the result file with a `-stale`
suffix, log `code_review_stale_result`, and keep waiting. A result that
names no head (a bare JSON block is a valid result, C.5) is taken as the
newest launch's result and parsed.

Every HALT this step raises about `/code-review` (no result in 4 hours,
ended twice with no result, the two-launch limit, C.4's second unparsed
result) first sets `context.code_review_status = "failed"` and
`context.code_review_invoked_head = null`, writes state, and logs
`code_review_halted {reason, head_sha}`. Status `"failed"` is not
`"running"`, so a re-invoke after such a HALT launches afresh.

At most two launches per head in total, counted from the
`code_review_invoked` events for that head logged after the latest
`code_review_halted` (all of them when there is none): the relaunch of
"Wait for the result" and C.4's "invoke the skill once more" share that
one second launch. A third sets the failed status, logs
`code_review_halted` and is a HALT. An invocation the skill rejects for
its extra text never started a review: it logs no `code_review_invoked`
and is not a launch, so the invocation that follows it keeps the same
`launch` number.

| `context.host_platform` | Skill | Invocation |
|---|---|---|
| `claude-code` | `code-review` | `Skill(skill="code-review", args="max --max-findings all <branch><read-only hint><dismissed hint><dry-run hint><map hint><settled hint><intent hint>")` |
| `codex`, `gemini`, `other` | (none) | Log `code_review_invoked {host, skipped: true}`; set `context.code_review_status = "skipped"`; run the lens agents and, beside them, one general reviewer (below), then go to D |

- **Unmapped host.** The lens agents exclude general bug hunting, so
  dispatch one `pr-reviewer` agent, `model: "sonnet"`, with the full
  `pr-loop-lib/references/adversarial-review-prompt.md` rendered as in E
  over `git diff --function-context <base_sha>..HEAD`; under `--dry-run`,
  over `git diff --function-context <base_sha> <tree>`, the snapshot
  tree step 02 "Dispatch" takes (or its fallback diff when the snapshot
  fails). Its findings take the place of the `/code-review` list in D,
  with ids `code-review:finding-<N>` and `source: "code-review"`, mapped
  as in C.1: `file` to `path`, `line` to `line`, `description` then a
  blank line and `recommendation` to `body`, its own `severity`, and
  `declared_risk` and `settled_item` as given. A `minor` finding in
  category `style` that cites no lens or rule is a nit, as in step 02
  "Action policy on findings".
- **Pass `max --max-findings all` every time.** With no level the skill
  reuses whatever level was typed last, and the default cap of 15 cuts
  findings the review already found, while every finding here must be
  fixed or declared. The cap setting is saved, so the user's own
  `/code-review` runs keep it until they pass `--max-findings default`.
- **Every PR gets `max`.** No tier, diff size, repo or cost estimate
  lowers the level, and the lens agents never stand in for this review.
- The target is `context.branch`, already committed in A, so the review
  covers the whole branch against its base.
- `<read-only hint>`: always append
  `. Reviewers are read-only: never stash, restore, check out, reset or edit anything in the working tree.`
- `<dismissed hint>`: always append
  `. After the JSON block, list the candidates you checked and dismissed, one line each with the reason.`
- `<dry-run hint>`: under `--dry-run` A committed nothing, so the
  branch alone misses the uncommitted work. Append
  `. Review the change a real run would commit, not only the branch head: its diff from <base_sha>, uncommitted and untracked files included, is <repo-root>/.pr-autopilot/branch-<slug>.diff. Review only the files in that diff.`
  (step 02 "Dispatch" writes that file; write it before this launch).
- `<map hint>`: when `context.context_map_path` is set, append
  `. Context map: <path>. Read it first and check the diff against each item it lists.`
- `<settled hint>`: when this run wrote the settled file, append
  `. Settled decisions: <path>. Do not argue for a different choice on a point one of them covers. When the code no longer matches an item, report that as an ordinary finding. When the choice as stated can crash a client, hide an outage or failure, or drop the caller's own data, report it with a summary that starts "Declared but risky: " followed by the item's opening words.`
- `<intent hint>`: when step 02 "Intent documents" lists any, append
  `. Intent documents: <paths>. Report where code, doc comments, API descriptions or tests contradict them.`
- Set `context.code_review_hints_rejected = false` before the launch.
  If the skill rejects the extra text, set it to `true`, log
  `code_review_hints_rejected`, and invoke again with
  `max --max-findings all <branch>`, plus `<dismissed hint>` (it gives E
  its input) and, under `--dry-run`, `<read-only hint><dry-run hint>`,
  where the working tree holds the only copy of the
  work. D then applies the settled items itself (D1).
  Under `--dry-run`, when that is also rejected, the review did not run:
  set `context.code_review_status = "skipped"`, write "/code-review did
  not run: it rejected the dry-run hint" in the review summary and the
  step 11 report, never "no findings", and go to D.
- Never pass `--comment` or `--fix`: findings stay local, and fixes go
  through the verified fixer path below.

Log `code_review_invoked {host, skill: "code-review", level: "max", invoked_at, head_sha, launch, task_id}`,
with `task_id` the background task's id when the launch returns one,
and set `context.code_review_invoked = true`,
`context.code_review_invoked_at` and `context.code_review_invoked_head`.

In the same turn, run the lens agents per step 02 "Dispatch", store
their merged findings and write the review-summary skeleton (step 02
"When to write"). Their fixes wait for D, so `/code-review` and the lens
agents all read the same commit.

### Wait for the result

When the skill returns its findings inline, go straight to saving the
result below. It may instead return at once with a note that it is
running in the background (for example "Running in the background as
@code-review"). That is a launch, not a result:

1. Set `context.code_review_status = "running"` and write state.
2. Once every lens agent has returned and the merged list is stored, end
   the turn. Do not poll, do not start C, do not start step 04.
3. The result arrives as the background task's completion notification;
   the run resumes from C. When the turn resumes for any other reason
   first:
   - More than 4 hours since `context.code_review_invoked_at` with no
     result: set the failed status and log `code_review_halted` (Launch),
     then HALT "HALT: /code-review max returned no result in 4 hours.
     The PR is not open. Re-invoke pr-autopilot to retry."
   - Otherwise look for the review among the host's running background
     tasks: by task id when the launch returned one, else by the skill's
     name (on Claude Code the launch says only "Running in the
     background as @code-review", with no id). Still listed as running:
     say so in one line and end the turn again. The host cannot list
     background tasks, or the answer is unclear: treat it as still
     running; never relaunch on an unknown.
   - The host lists it as ended (completed with no usable result,
     failed, or stopped): relaunch once (launch 2), subject to the
     two-launch limit; a second such end sets the failed status, logs
     `code_review_halted` (Launch) and is the HALT "returned no result".

   With no later turn nothing wakes the run: the wait is bounded only
   when a turn arrives, and the user is told at the end of the launch
   turn that the run continues when the review reports. Do not use
   `ScheduleWakeup` here.

Save the result text to
`<repo-root>/.pr-autopilot/branch-<slug>-code-review.md` and to
`context.code_review_raw_output`.

## C — Parse

1. **JSON (current format).** Take the first fenced ```` ```json ````
   block and parse it as an array. Each element has `file` (string),
   `line` (integer or null), `summary` (string) and usually
   `failure_scenario` (string). For element N (1-indexed) record:
   - `id: "code-review:finding-<N>"`
   - `path: <file>`, `line: <line>` (integer, never a string)
   - `body: <summary>` followed by a blank line and `<failure_scenario>`
   - `severity: "important"`, `source: "code-review"`
   - `declared_risk: true` when `summary` starts with
     "Declared but risky:"; `settled_item` is the settled file line
     whose opening words follow that prefix
2. **Numbered list (older format).** With no JSON block, apply the
   numbered-finding parser in `pr-loop-lib/steps/03-triage.md` Filter
   B.5 Stage 1. An item whose text starts "Declared but risky:" sets
   `declared_risk: true` and `settled_item` as in 1.
3. **Zero findings.** An empty array, or a result that says it found
   nothing, is success: record "no findings" in the review summary,
   collect any dismissed candidates (step 5), set the status below, then
   go to D, which still handles the lens findings.
4. **Unparsed.** Any other non-empty result is a failure, never "no
   findings". Log `code_review_parse_failed {raw_prefix, reason}`,
   invoke the skill once more (the second launch for this head, shared
   with "Wait for the result"), and on a second failure set the failed
   status and log `code_review_halted` (Launch), then HALT:
   "HALT: /code-review output could not be parsed. Raw output: <path>.
   The PR is not open." Never open a PR over findings nobody read.
5. **Checked and dismissed.** The prose after the JSON block lists
   candidates the review refuted or dropped and areas it checked clean.
   Store each refuted or dropped candidate in
   `context.code_review_dismissed[]` as `{summary, reason}` and write
   them all to the review summary under "Checked and dismissed by
   /code-review". E re-checks them. A result that is only the JSON
   block, with no prose after it, is a successful parse (never
   `code_review_parse_failed`) that lists no dismissed candidates: set `context.code_review_dismissed = []` and
   write "none listed by /code-review" under that heading.

Set `context.code_review_status = "done"`.

## D — Fix or declare every finding

1. **Merge the lists** per `pr-loop-lib/references/merge-rules.md`
   "When to invoke the merge" (pre-open). The lens list is step 02's
   `merged`, already folded across agents. For each `/code-review`
   finding that matches a lens finding, log
   `triage_dedup_hit {feedback_id, preflight_match_id, source: "code-review"}`,
   record the `/code-review` finding with status `duplicate` naming the
   lens id, and append its failure scenario to the lens finding. The
   kept lens finding takes the higher severity of the two, is declared
   but risky when either is, takes the `settled_item` and `check_id` of
   whichever carries one, and keeps any lens id the dropped finding
   cited.

   Then add step 01.5's skipped points. Each `context.simplify_skipped`
   entry becomes a candidate finding: `id: "simplify-<N>"` (1-indexed),
   `source: "simplify"`, `severity: "important"`, `path`, `line`, and
   `body` the summary followed by "Skipped by /simplify because: <reason>".
   One that names the same file and the same failure as a lens or
   `/code-review` finding is recorded with status `duplicate` naming
   that finding, folded into it the same way, and logged as
   `triage_dedup_hit` with `source: "simplify"`; the rest are dispatched
   like any other finding.

   **Settled items.** A finding or candidate that only restates a
   settled item (the code matches the statement and none of the three
   consequence tests holds) is recorded with status `declared` and that
   `settled_item`. It is never dispatched, and F adds no declaration for
   it: the item is already declared. One whose code no longer matches
   the statement is an ordinary finding. When
   `context.code_review_hints_rejected` is true, `/code-review` never saw
   the settled file, so test each `/code-review` finding on the same file
   as a settled item's cited `<file>:<line>` and within 3 lines of it:
   the code no longer matches the statement → an ordinary finding; one
   of the three consequence tests holds → `declared_risk: true` with
   that `settled_item`; neither → it restates the item, as above.

   Add every declared-but-risky finding that is not a `duplicate` to
   `context.needs_human_items`, with its id, file, line, summary, and the
   consequence as the reason, so step 11 lists it under "Needs your
   input".
2. **Dispatch everything else in one round:** every lens finding that is
   not a nit (step 02 "Action policy on findings"), every
   `/code-review` finding that is not a duplicate, and every simplify
   candidate that is not a duplicate. Never dispatched: a nit, a
   declared-but-risky finding from any source (step 02 "Action policy
   on findings"), and a finding recorded `declared` for a settled item
   (D1). `/code-review` reports bugs, not style, so none of its findings
   is a nit; the general reviewer of an unmapped host follows the nit
   rule (B). Dispatch a
   fixer per finding with `pr-loop-lib/steps/04-dispatch-fixers.md`:
   its "Rolling dispatch", its agent types and models, and its "Unit
   base" and "Rollback", which give each verifier's diff and every
   rollback, with or without `--dry-run`. A unit whose base cannot be
   recorded is not dispatched and its findings are `needs-human` (step
   04 "Unit base"); there is no `HEAD` fallback. The post-dispatch
   invariants are `P02.*` (the
   ids live in `context.internal_review_findings[].fixer_feedback_id`).
   Every fixer return is verified. Fixers do not build or test: D3 runs
   step 04.5 once, after the wave. Nothing is posted anywhere.

   Under `--dry-run` the files a fixer may change also hold the user's
   uncommitted implementation. Tell each fixer in its dispatch text to
   edit only files in the review diff or new files. Before dispatching,
   also when nothing is dispatched, take a snapshot tree ("Dry-run") and
   store its id in `context.fix_round_base_sha`: E's base, never a
   rollback source or a verifier's base.
3. Run `pr-loop-lib/steps/04.5-local-verify.md` once, after every unit
   has returned and been verified, when any fixer changed files, on the
   union of this dispatch's `files_changed`, passed as its file list
   (before the loop `context.files_changed_this_iteration` is empty and
   the step would otherwise skip).
4. **Outcomes** map to statuses per step 02 "Action policy on
   findings" (`fixed` / `fixed-differently` when verified, `declared`,
   `needs-human`), recorded in `context.internal_review_findings` with
   `source: "preflight"` for lens findings, `"simplify"` for step
   01.5's candidates, `"code-review"` for the
   rest, and `"fix-round"` for findings that arrive from E. Record them
   from the final verdicts after verification: a fix that verification
   rolled back is `needs-human`. Then check `P02.*` for this dispatch,
   before D5 commits: `P02.1` reads the `fixer_feedback_id`s recorded
   here, and `P02.2` and `P02.3` are checked against the bases named in
   `invariants.md`, with or without `--dry-run`.
5. **Commit locally** when the working tree changed. Secret scan the
   changed files first (BLOCKING, as in A). Subject
   `Address pre-open review findings`; body one bullet per fix (finding
   plus what changed), then the "Kept on purpose" block for declarations
   not yet in a commit. Record `context.fix_round_base_sha` (HEAD before
   this commit) and set `context.head_sha` after it. No push.

   Under `--dry-run` write the message to the dry-run directory, commit
   nothing, and take a second snapshot tree into
   `context.fix_round_head_tree` whenever D2's snapshot succeeded. When
   no fixer changed a file it equals the D2 tree and E's diff is empty.

Append the per-finding outcomes to the review summary under "## Lens
review", "## /simplify skipped points" and "## /code-review (pre-open)",
and every declared-but-risky finding under "## Declared but risky".

## E — Fix-round review

Fixes written after a review are reviewed by nobody unless this runs;
reviewers find many of their points in exactly that code.

Runs when D's fixers changed the code (a fix commit, or under
`--dry-run` a head tree that differs from the D2 tree), or
`context.code_review_dismissed` is non-empty. One `pr-reviewer` agent,
`model: "sonnet"` (passed explicitly), with
`pr-loop-lib/references/adversarial-review-prompt.md` rendered as:

- `{{BASE_SHA}}` → `context.fix_round_base_sha` (or `context.head_sha`
  when D changed nothing; under `--dry-run`, always the D2 tree)
- `{{HEAD_SHA}}` → `context.head_sha`; under `--dry-run`,
  `context.fix_round_head_tree`, with a note that both ids are trees of
  the working tree and that the files on disk are the head side
- `{{DIFF}}` → `git diff --function-context <base>..<head>`; under
  `--dry-run`, `git diff --function-context <base tree> <head tree>`
  (empty when D changed nothing)
- `{{WHAT_WAS_BUILT}}` → "Fixes for the review findings listed in the
  intent documents. Check that each fix closes its finding at every site
  that has the same problem, and that it breaks nothing nearby. Then
  check each refuted candidate listed there against the code at
  head_sha, and report it when the refutation is wrong."
- `{{INTENT_DOCS}}` → the intent documents the lens agents received, then a "Findings these
  fixes address" list (id, summary, failure scenario) and a "Candidates
  /code-review refuted" list (`code_review_dismissed`)
- `{{SETTLED}}` → the settled file from B rewritten with D's
  declarations. Under `--dry-run` those declarations are in no commit,
  so leave the file as B wrote it and pass its lines plus D's
  declarations inline, for this review only.
- `{{CONTEXT_MAP}}` → as in step 02; `{{LENS_GUIDANCE}}` → the single
  fix-round block of step 02 "Lens guidance rendering"

When `context.code_review_dismissed` is empty, leave the last sentence
of `{{WHAT_WAS_BUILT}}` and the refuted list out, and write the reason
under "## Fix-round review", never that the check ran: "/code-review
listed no dismissed candidates" only when `code_review_status` is
`done`; when it is `skipped`, "Refuted-candidate check skipped:
/code-review did not run".

Treat its findings like step 02's: nits (`minor` + `style`) are
recorded only. Apply D1's "Settled items" rule and its
`needs_human_items` rule to them, list each declared-but-risky one under
"## Declared but risky", and send everything else through D2-D5 again with ids
`fix-round-<R>-<N>`, `source: "fix-round"` in place of D4's source
mapping, and `P02.*` checked after D4 on each fix-round dispatch. At most 2 fix rounds; a finding still open after
round 2 becomes `needs-human`. Under `--dry-run` each later round's
`fix_round_base_sha` is the previous round's head tree, in place of a
new D2 snapshot, and its D5 takes a new head tree.
Record outcomes under "## Fix-round review" in the review summary.

## F — Declarations

Build `context.declarations[]` before step 04 fills the body. Sources:

- every `internal_review_findings` entry with status `declared` and no
  `settled_item` (one with a `settled_item` restates a choice already
  declared)
- `context.spec_alignment_notes` that describe a deliberate deviation
  from the spec
- the context map's "Declared differences"
- work the conversation or spec puts out of this PR's scope (`kind:
  "scope"`, naming where it is tracked when that is known)

Each statement is one present-tense sentence a reviewer can check: what
the code does, and why it stays that way. No history of how the choice
was reached.

Every declaration must appear in a commit message, because some review
bots read commits and never the PR body. Set `in_commit` to the commit
whose body carries it. When some declaration still has
