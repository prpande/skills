# Step 03.5 — Pre-open review

Every review runs before the PR exists, so a finding is fixed or
declared before any human or bot sees the code. This step commits the
work locally, runs the host's `/code-review` at `max`, fixes or declares
every finding, reviews those fixes, and writes the kept decisions into
commit messages. Nothing is pushed here; step 04 pushes and opens the PR.

`pr-followup` never runs this step. Under `--dry-run`, A runs its
secret scan and writes the commit message to the dry-run directory
without committing; B-F are skipped and logged as
`code_review_invoked {host, skipped: true, reason: "dry-run"}`.

## A — Commit the work locally

1. **Secret scan (BLOCKING).** Apply
   `pr-loop-lib/references/secret-scan-rules.md` to every file about to
   be staged:
   - `context.uncommitted` (the "related" subset from step 01)
   - files modified by step 02 fixers
   - `context.spec_updates` files (step 03)
   - `context.simplify_files` (folded `/simplify` edits from step 01.5,
     staged **unconditionally**, never re-filtered for relatedness)

   Any match → halt with the BLOCK message from the secret-scan
   reference. Do not stage.
2. Stage exactly those paths with `git add <specific paths>`. Never
   `git add .` or `git add -A`. When nothing is staged (all work was
   already committed), skip to 3.
3. Commit-message convention: `CONTRIBUTING.md` guidance if present,
   else the pattern of the last 20 commits on the base branch (`feat:`,
   `fix:`, ...), else a short imperative subject about the "why".
   Subject from `context.what_was_built` plus the dominant change
   category. Body: one paragraph pointing to the motivating spec files,
   if any, then the "Kept on purpose" block (section F) for the
   declarations step 02 made.
   ```bash
   git commit -F <message file>
   ```
   Commit signing follows the user's git config. Never pass
   `--no-verify`, `--no-gpg-sign` or `-c commit.gpgsign=false`; surface a
   signing failure instead.
4. Set `context.head_sha` to `git rev-parse HEAD`.

## B — `/code-review` at max

| `context.host_platform` | Skill | Invocation |
|---|---|---|
| `claude-code` | `code-review` | `Skill(skill="code-review", args="max <branch><map hint>")` |
| `codex`, `gemini`, `other` | (none) | Log `code_review_invoked {host, skipped: true}`; set `context.code_review_status = "skipped"`; go to F |

- **The level is `max`, named explicitly, every time.** With no level
  the skill reuses whatever level was typed last, and it picks max only
  when a skill asks for it. Never pass another level.
- The target is `context.branch`, already committed in A, so the review
  covers the whole branch against its base.
- `<map hint>`: when `context.context_map_path` is set, append
  `. Context map: <path>. Read it first and check the diff against each item it lists.`
  If the skill rejects the extra text, invoke again with
  `max <branch>` only.
- Never pass `--comment` or `--fix`: findings stay local, and fixes go
  through the verified fixer path below. Never pass `--max-findings`: it
  changes the user's saved setting.

Log `code_review_invoked {host, skill: "code-review", level: "max", invoked_at}`
and set `context.code_review_invoked = true`,
`context.code_review_invoked_at`.

### Wait for the result

The skill may return at once with a note that it is running in the
background (for example "Running in the background as @code-review").
That is a launch, not a result.

1. Set `context.code_review_status = "running"` and write state.
2. End the turn. Do not poll, do not start C, do not start step 04. The
   result arrives as a task notification, and the run resumes from C.
3. As a fallback, arm `ScheduleWakeup` at 3600 s. A wakeup with no
   result yet re-arms once; a second wakeup with no result invokes the
   skill once more, and a third HALTs: "HALT: /code-review max returned
   no result. The PR is not open. Re-invoke pr-autopilot to retry."

Save the result text to
`<repo-root>/.pr-autopilot/branch-<slug>-code-review.md` and to
`context.code_review_raw_output`.

## C — Parse

1. **JSON (current format).** Take the first fenced ```` ```json ````
   block and parse it as an array. Each element has `file` (string),
   `line` (integer or null), `summary` (string) and usually
   `failure_scenario` (string). For element N (1-indexed) record:
   - `id: "code-review:finding-<N>"`
   - `path: <file>`, `line: <line>` (integer, never a string)
   - `body: <summary>` followed by a blank line and `<failure_scenario>`
   - `severity: "important"`, `source: "code-review"`
2. **Numbered list (older format).** With no JSON block, apply the
   numbered-finding parser in `pr-loop-lib/steps/03-triage.md` Filter
   B.5 Stage 1.
3. **Zero findings.** An empty array, or a result that says it found
   nothing, is success: record "no findings" in the review summary and
   go to E.
4. **Unparsed.** Any other non-empty result is a failure, never "no
   findings". Log `code_review_parse_failed {raw_prefix, reason}`,
   invoke the skill once more, and on a second failure HALT:
   "HALT: /code-review output could not be parsed. Raw output: <path>.
   The PR is not open." Never open a PR over findings nobody read.
5. **Checked and dismissed.** The prose after the JSON block lists
   candidates the review refuted or dropped and areas it checked clean.
   Store each refuted or dropped candidate in
   `context.code_review_dismissed[]` as `{summary, reason}` and write
   them all to the review summary under "Checked and dismissed by
   /code-review". E re-checks them.

Set `context.code_review_status = "done"`.

## D — Fix or declare every finding

1. **Dedup.** Compute each finding's `description_hash` per step 02
   "Per-finding `description_hash`". A hash equal to a
   `preflight_passes.merged[].description_hash` is logged as
   `triage_dedup_hit {feedback_id, preflight_match_id, source: "code-review"}`
   and recorded with status `duplicate`, naming the preflight id.
2. **Dispatch every other finding.** `/code-review` reports bugs, not
   style, so none is a nit. Dispatch a fixer per finding with
   `pr-loop-lib/steps/04-dispatch-fixers.md`; the post-dispatch
   invariants are `P02.*` (the ids live in
   `context.internal_review_findings[].fixer_feedback_id`). Every fixer
   return is verified. Nothing is posted anywhere.
3. **Outcomes**, recorded in `context.internal_review_findings`
   (`source: "code-review"`):
   - `fixed`, `fixed-differently` (verified): done.
   - `not-addressing` or `replied` (a verifier `feedback-wrong` ends as
     `not-addressing`): status `declared`, plus a
     `context.declarations[]` entry as in step 02 "Action policy on
     findings".
   - `needs-human` (a verifier `partial` included) or `ui-deferred`:
     status `needs-human`, listed by step 04 under "Open questions for
     reviewers".
4. Run `pr-loop-lib/steps/04.5-local-verify.md` when any fixer changed
   files.
5. **Commit locally** when the working tree changed. Secret scan the
   changed files first (BLOCKING, as in A). Subject
   `Address pre-open review findings`; body one bullet per fix (finding
   plus what changed), then the "Kept on purpose" block for declarations
   not yet in a commit. Record `context.fix_round_base_sha` (HEAD before
   this commit) and set `context.head_sha` after it. No push.

Append the per-finding outcomes to the review summary under
"## /code-review (pre-open)".

## E — Fix-round review

Fixes written after a review are reviewed by nobody unless this runs;
reviewers find many of their points in exactly that code.

Runs when D committed fixes, or `context.code_review_dismissed` is
non-empty. One `pr-reviewer` agent, `model: "sonnet"`, with
`pr-loop-lib/references/adversarial-review-prompt.md` rendered as:

- `{{BASE_SHA}}` → `context.fix_round_base_sha` (or `context.head_sha`
  when D committed nothing)
- `{{HEAD_SHA}}` → `context.head_sha`
- `{{DIFF}}` → `git diff --function-context <base>..<head>` (empty when D
  committed nothing)
- `{{WHAT_WAS_BUILT}}` → "Fixes for the review findings listed in the
  intent documents. Check that each fix closes its finding at every site
  that has the same problem, and that it breaks nothing nearby. Then
  check each refuted candidate listed there against the code at
  head_sha, and report it when the refutation is wrong."
- `{{INTENT_DOCS}}` → the spec text from step 02, then a "Findings these
  fixes address" list (id, summary, failure scenario) and a "Candidates
  /code-review refuted" list (`code_review_dismissed`)
- `{{CONTEXT_MAP}}`, `{{LENS_GUIDANCE}}` → as in step 02

Treat its findings like step 02's: nits (`minor` + `style`) are
recorded only, everything else goes through D2-D5 again with ids
`fix-round-<R>-<N>`. At most 2 fix rounds; a finding still open after
round 2 becomes `needs-human`. Record outcomes under "## Fix-round
review" in the review summary.

## F — Declarations

Build `context.declarations[]` before step 04 fills the body. Sources:

- every `internal_review_findings` entry with status `declared`
- `context.spec_alignment_notes` that describe a deliberate deviation
  from the spec
- the context map's "Declared differences"
- work the conversation or spec puts out of this PR's scope (`kind:
  "scope"`, naming where it is tracked when that is known)

Each statement is one present-tense sentence a reviewer can check: what
the code does, and why it stays that way. No history of how the choice
was reached.

Every declaration must appear in a commit message, because some review
bots read commits and never the PR body. Set `in_commit` to the commit
whose body carries it. When some declaration still has
`in_commit: null` after A-E, make one more local commit:

```bash
git commit --allow-empty -F <message file>   # subject: Record deliberate choices kept after review
```

The "Kept on purpose" block:

```
Kept on purpose:
- <statement> (<file>:<line>)
```

## Invariants

After this step, check per `pr-loop-lib/references/invariants.md`:
`P02.*` for each dispatch in D and E, and `S35.*`.
